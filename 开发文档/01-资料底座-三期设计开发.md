# M1 资料底座：三期设计开发

依赖：00 总体架构。消费者：M2 合同检查、M3 纠纷方案、M4 来源展示。本文不包含已经核验的具体法条、热线或地方受理承诺。

## 1. 模块目标

为每一条法律解释和渠道建议提供可追溯、可筛选、有核验日期的资料。知识库是经过审核的资料集合，不是未经筛选的网页缓存。不同地域、历史版本及渠道职责不能混用。

## 2. 一期：JSON 资料与确定性筛选

### 2.1 交付物

- 一个试点城市及国家层面的押金相关资料。
- 押金未退、部分扣款两类场景的法条—解释—规则映射。
- 针对个人房东、中介、公寓经营者的渠道适用规则。
- 来源展示接口与构建前检查脚本。
- 独立合成测试资料，禁止混入真实已核验资料包。

### 2.2 资料结构

`KnowledgeBundle` 以 `version`、`builtAt`、`supportedCities`、`sources`、`channels`、`rules` 为顶层字段。version 随审核资料变化递增，运行期只读，不接受用户修改。

来源记录：

```ts
type SourceRecord = {
  id: string;
  title: string;
  kind: 'law' | 'regulation' | 'judicial_interpretation' |
    'local_rule' | 'official_guidance' | 'official_service';
  issuer: string;
  officialUrl: string;
  jurisdiction: { level: 'national' | 'local'; cityCodes: string[] };
  validFrom: string | null;
  validUntil: string | null;
  validityStatus: 'effective' | 'repealed' | 'not_yet_effective' | 'unknown';
  reviewedAt: string;
  reviewDueAt: string;
  reviewStatus: 'draft' | 'verified' | 'needs_review';
  reviewer: string;
  scenarios: string[];
  articles: Array<{
    id: string;
    label: string;
    text: string;
    interpretation: string;
    applicabilityNotes: string[];
  }>;
};
```

`validUntil = null` 表示未记录结束日期，不等于已确认永久有效；效力还需由 validityStatus、核验状态和事件日期联合判断。official_service 页面可能没有法规生效日期，不作为“有法律效力”的条文引用。

渠道记录：

```ts
type ChannelRecord = {
  id: string;
  name: string;
  cityCode: string;
  kind: 'negotiation' | 'enterprise' | 'consumer' | 'administrative' |
    'mediation' | 'legal_consultation' | 'legal_aid' | 'litigation';
  receiver: string;
  officialUrl: string | null;
  phone: string | null;
  acceptedScenarios: string[];
  counterpartyTypes: Array<'individual_landlord' | 'agency' | 'operator' | 'unknown'>;
  eligibilityConditions: string[];
  exclusions: string[];
  requiredEvidenceIds: string[];
  sourceRefs: Array<{ sourceId: string; articleIds: string[] }>;
  reviewedAt: string;
  reviewDueAt: string;
  reviewStatus: 'draft' | 'verified' | 'needs_review';
};
```

渠道条件通过结构化规则计算，字符串条件仅供用户解释，不以字符串解析实现资格判断。联系电话和链接从审核记录取值；没有核验时显示“尚未核实”，不让模型补全。

### 2.3 核验要求

1. 从官方原文或官方服务入口采集，记录部门、发布日期、生效/失效信息和适用范围。
2. 法规原文与产品解释分字段保存；解释不能伪装为法条原文。
3. 核实渠道受理对象及地域，区分咨询、转办、调解、行政处理、裁判的不同作用。
4. 对法律援助单独核实援助事项和资格条件；提供咨询入口不代表符合代理援助资格。
5. 记录核验人及下一次复核日期，单人团队至少进行独立的二次复核并留记录。
6. 链接失效、政策修订、职责不明或复核逾期时转 needs_review；严格建议不引用这些记录。

### 2.4 资料筛选顺序

```text
reviewStatus=verified 且未超过复核日期
→ 地域匹配（国家资料或明确覆盖请求城市）
→ 场景匹配
→ 事件日期与资料版本匹配
→ 读取与业务规则相关的具体条款
→ 输出允许引用的 sourceId/articleId 集合
```

事件日期未知时，仅提供条件性说明并提示补充；不能直接以今天有效的法律版本解释历史事实。旧版本不直接删除，保留适用时间及取代关系。

未支持城市返回 coverage=unsupported，保留一般证据清单，不伪造当地渠道。已支持城市但某类法律依据不足返回 limited；一般合同沟通建议可独立存在，但不能带上不相关的法条。

### 2.5 接口

`GET /functions/v1/app?action=config` 返回 `supportedCities`、`supportedScenarios`、`knowledgeVersion`、`features`、`limits`。城市必须有对应的审核通过资料和渠道，不因创建配置项即显示为已支持。

`GET /functions/v1/app?action=sources&cityCode=...&scenario=...` 返回该城市和场景下可公开的已审核来源；可选 eventDate 按事件日期筛选，不传则仅用于浏览资料并保留各版本效力区间，不能替代业务分析中的时间适用性判断。结果含 id、标题、部门、网址、核验日期、效力说明及 articles；不包含内部备注或未审核草稿。

业务响应直接携带实际采用的 `references: SourceRecordPublic[]`，前端不依赖展示时再次查询最新资料。来源页可以查询新版本，但必须与原报告的 knowledgeVersion 区分。

### 2.6 构建与发布

- 人工维护 knowledge 下的 JSON；构建脚本校验字段、引用闭合及地域一致性。
- 构建输出自包含 TS 数据快照到函数目录，不依赖生产运行时读取项目外路径。
- 已发布包不修改；资料变更生成新版本并重新准备发布。
- 真实来源 URL 只从实际采集结果写入，不在开发文档中猜测。

### 2.7 验收

- 不存在悬空 sourceId、articleId、channelId 或重复ID。
- 城市 A 不得到城市 B 专属渠道；国家资料不自动推导地方执行职责。
- 未生效、已失效、效力未知、未核验和逾期资料不会作为确定性依据。
- 合同历史日期选择对应版本，日期不明返回待核实。
- UI 可打开实际来源并定位到展示的条文编号；来源中没有的条文不可能被响应引用。

## 3. 二期：场景扩展与版本管理

### 3.1 新增资料范围

提前退租、维修责任、额外费用、中介服务、入住/退租交接。每个场景具备问题清单、证据要求、规则适用条件和反例。一个城市覆盖做完整后再增加城市，不以抓取网页数量作为完成指标。

### 3.2 新增结构

- `supersedesId`：来源版本关联；没有关联时为空。
- `ruleVersion`：规则版本，与资料版本分别记录。
- `scenarioRequirements`：场景需要的输入与证据字段。
- `changeLog`：变更类型、审核日期、影响的场景和渠道。

一期字段保持含义。运行响应增加可选 ruleVersion，前端仍可消费一期数据。政策变更必须同步检查关联规则与模板，不能只替换原文。

### 3.3 实现步骤

1. 以场景为单位完成资料和规则映射。
2. 增加跨场景引用检测及冲突规则检查。
3. 为新增城市生成覆盖报告，列出已支持和未支持场景。
4. 更新快照后重跑涉及场景，不要求无关功能全部重测。

### 3.4 验收

新场景的正例、反例和信息不足样例均可追溯至审核资料。相同词汇在不同场景下不得错误复用结论，例如押金扣除与提前退租责任分开判断。

## 4. 三期：混合检索与索引服务

### 4.1 技术方案

默认托管 PostgreSQL + pgvector；使用服务端 HTTPS 检索接口，不在浏览器暴露数据库连接或管理凭据。不假定 Sites 内置数据库已开启扩展。上线前验证可用性，不满足时再评估 Qdrant。

人工审核 JSON 仍是权威源，向量只是派生索引。检索故障可以回到已验证的结构化筛选，并标注 limited；不是让模型凭记忆填补依据。

### 4.2 逻辑数据表

| 表 | 主键/关键字段 | 用途 |
| --- | --- | --- |
| source_versions | source_id + version；地域、效力区间、审核状态 | 版本化来源 |
| articles | article_id + source_version；原文、编号、hash | 引用的最小权威单元 |
| chunks | chunk_id；article_id、ordinal、text、hash | 召回单元，保留到原条文的关联 |
| embeddings | chunk_id + index_version；embedding、model、dimension | 向量索引 |
| index_manifests | index_version；knowledge_version、model、状态 | 原子切换已完成索引 |

维度依实际 Embedding 模型确定，设计阶段不固定。运行凭据只读；入库由独立受控脚本执行，不开放匿名管理端点。

### 4.3 入库流程

人工核验 → 原文按条款切分 → 内容hash去重 → Embedding → 写入候选索引 → 评测 → 切换 active index。失败不影响上一可用版本；重建新版本而非原地混合模型。仅当资料规模与处理需求证明必要时才用 Python 离线脚本。

### 4.4 检索流程

地区/场景/时间等元数据强约束 → 关键词与向量分别召回 → 去重融合 → 读取权威条文原文 → 交给业务规则及模型解释。默认每路候选上限20、融合后最多8个片段、上下文总长度上限12000字符，具体阈值以评测调整；这是应用初始配置，不是平台能力保证。

未知资格或未知事件日期不能通过降低相似度阈值解决。检索结果只作为候选，不作为渠道受理资格判断。

### 4.5 验收与回滚

建立人工标注的押金/维修/退租/收费查询集，覆盖地域错误、历史版本、无答案和近义表达。比较结构化基线与混合检索的相关条文召回、错误地域数、无答案正确拒答和引用有效性；引用合法性必须全通过，任何跨地域/失效条文进入确定性结论均阻止上线。

记录实际评测结果后决定是否启用向量检索，不因接上数据库即声称提升准确率。回滚只切回已验证的索引/快照版本，不删除用户之外的共享数据。

## 5. 跨模块契约

M2/M3 只能引用本次过滤后允许的 sourceId/articleId；最终结果附带同一 knowledgeVersion 的引用快照。M4 只展示后端回填的 URL/电话。缺少资料时，业务层返回 limited/unsupported；资料层不制造“默认全国适用”或“通用消费者渠道”。
