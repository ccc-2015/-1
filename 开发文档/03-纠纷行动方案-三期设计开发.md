# M3 纠纷行动方案：三期设计开发

依赖：00 总体架构、01 资料底座。可独立使用，不要求用户先做合同检查；M2提取信息若转入本模块，需经用户确认，不能作为未经确认的事实。

## 1. 一期：押金未退与部分扣款

### 1.1 目标

将用户描述转换为“事实摘要—还缺什么材料—现在怎么沟通—符合条件的下一步”。不设置统一热线排行榜，不以证据不足否定权利，不承诺受理或结果。

### 1.2 请求协议

`POST /functions/v1/app?action=diagnose-dispute`，JSON，请求实际字节上限64 KiB。

```ts
type EvidenceStatus = 'available' | 'missing' | 'unknown' | 'not_applicable';
type DisputeInput = {
  cityCode: string;
  eventDate: string | null;
  scenario: 'deposit_not_returned' | 'deposit_deducted';
  counterpartyType: 'individual_landlord' | 'agency' | 'operator' | 'unknown';
  depositAmountCents: number | null;
  disputedAmountCents: number | null;
  tenancyEnded: 'yes' | 'no' | 'unknown';
  handoverStatus: 'completed' | 'not_completed' | 'disputed' | 'unknown';
  returnDueStatus: 'due' | 'not_due' | 'unclear';
  deductionReason: string;
  evidence: Array<{ evidenceId: string; status: EvidenceStatus }>;
  priorActions: Array<{
    type: 'negotiation' | 'written_notice' | 'enterprise_complaint' |
      'mediation' | 'administrative_contact' | 'consumer_contact' | 'legal_consultation';
    outcome: 'not_started' | 'pending' | 'resolved' | 'unresolved' | 'unknown';
  }>;
  goal: 'return_deposit' | 'explain_deduction' | 'prepare_evidence' | 'understand_options';
  narrative: string;
};
```

deductionReason 上限1000字符，narrative 上限3000字符。金额允许未知，已知时为非负安全整数分。争议额超过押金时提示确认，不直接拒绝：其中可能包含其他费用，需拆分明细。priorActions 无记录表示尚未填写，不能默认已协商失败；同一类型只保留用户确认的当前状态。

returnDueStatus 是用户自述，不等同于法律认定到期。没有日期依据时返回待核实。渠道资格涉及援助等条件时采用渐进补充问答，不在一期默认收集身份证、收入证明或完整住址。

### 1.3 输出协议

```ts
type DisputePlan = {
  factsSummary: Array<{ label: string; value: string; origin: 'user_statement' }>;
  missingFacts: Array<{ field: string; question: string; reason: string }>;
  evidenceChecklist: Array<{
    evidenceId: string;
    title: string;
    status: EvidenceStatus;
    priority: 'essential' | 'helpful';
    reason: string;
    preparationTip: string;
  }>;
  communication: { text: string; placeholders: string[]; warnings: string[] };
  nextSteps: PathStep[];
  conditionalOptions: PathStep[];
  excludedOptions: Array<{ channelId: string; reason: string }>;
  references: SourceRecordPublic[];
};

type PathStep = {
  stepId: string;
  channelId: string;
  eligibility: 'eligible' | 'needs_check';
  title: string;
  why: string;
  preparations: string[];
  contact: { officialUrl: string | null; phone: string | null };
  sourceRefs: Array<{ sourceId: string; articleIds: string[] }>;
  after: {
    resolved: string;
    unresolvedStepIds: string[];
    pending: string;
  };
};
```

nextSteps 只包含当前 eligible 的步骤，按建议优先级最多展示3项；conditionalOptions 容纳 needs_check，包含“当前资格待核实”或“前一步未解决才适用”的后续选项，不能显示为当前必走步骤。excludedOptions 仅返回与用户相关的候选，不罗列所有不适用渠道。协商类步骤也必须有预置 channelId，可无外部联系方式。

### 1.4 证据目录

一期至少定义以下 evidenceId，并由 M1 场景配置引用：

| evidenceId | 内容 | 用途 |
| --- | --- | --- |
| lease_contract | 合同及补充约定 | 核实押金、退租与扣款约定 |
| deposit_payment | 押金支付记录 | 核实支付对象、金额和时间 |
| return_agreement | 退还安排及承诺 | 判断双方约定，不代替法律结论 |
| checkin_condition | 入住照片/交接记录 | 证明原有状态 |
| checkout_handover | 退租交接及钥匙移交记录 | 证明交接及退租事实 |
| deduction_detail | 扣款明细和对方提出的凭证 | 明确争议项目 |
| communications | 完整沟通与催告记录 | 整理经过和双方表述 |

证据建议强调合法获取、保存原件及上下文，不指导伪造、篡改或获取无关个人资料。not_applicable 不计入缺项；unknown 提醒核实；missing 给出可行的补充方式，不假设一定能补回历史照片。

### 1.5 路径计算规则

规则顺序：事实完整性检查 → 地域/事件日期筛选 → 对方身份与事项资格判断 → 已采取行动状态 → 时间/程序敏感因素 → 推荐顺序。由服务端确定，AI只润色说明。

| 条件 | 处理 |
| --- | --- |
| 对方身份未知 | 补问签约和收款主体，涉及经营者资格的路径列入待核实 |
| 退还条件或是否到期不明 | 先核实合同及交接事实，不直接指称逾期违法 |
| 未拿到扣款明细 | 优先生成索取项目、标准和凭证的协商文本 |
| 个人之间租赁争议 | 不默认满足消费者渠道受理条件；按当地核验资料判断 |
| 经营性中介/公寓 | 先区分服务争议与租赁争议，再匹配渠道，不因主体经营就必然适用某渠道 |
| 已协商无果 | 不把“再协商一次”固定排第一，推荐符合条件的后续途径 |
| 已有渠道受理、仍待回复 | 提示保存编号、按已核实流程跟进，不自动重复投诉 |
| 法律援助资格未知 | 展示咨询/资格核实入口，不承诺免费代理 |
| 正式程序或期限可能敏感 | 不强制用户走完整协商链，提示及时取得专业意见 |
| 地区不支持/资料失效 | 输出一般留证和事实梳理，暂停当地特定推荐 |

不以金额大小单独决定能否诉讼或获得援助。书面沟通的回复时间如无明确法律或程序依据，只能表述为“可协商的回复期限”，不能伪称法定期限。诉讼时效等涉及完整时间线的问题未确定时不自行计算截止日。

每条规则以 `ruleId`、输入条件、资格结果、排序组、解释模板和 sourceRefs 管理。排序采用明确优先组加稳定次序，不用不可解释的模型分数。已排除的渠道不可能在润色后重新出现。

### 1.6 协商模板

一期使用确定性模板，避免为简单文本额外调用模型。模板结构：身份关系的必要描述 → 已核实的用户陈述 → 明确请求 → 索取明细/凭证 → 联系与后续协商安排。

未知值保留 `[请补充退租日期]` 等占位符；前端提示填写后再发送。不填入未经用户提供的损坏原因、恶意判断、违法结论或法律期限。模板仅供用户复制与编辑，系统不代发。

### 1.7 验收

- 相同事实与资料版本得到相同渠道资格与顺序。
- 个人房东与中介服务争议能得到不同候选路径。
- 未知证据与明确缺失不会混为一谈。
- 已协商失败、待受理、未协商的下一步不同。
- 返回的联系方式均存在于核验资料，不来自模型。
- 每个 unresolvedStepId 能定位到本响应中的步骤；路径无循环，未解决分支无效时明确需补充事实。
- 模板不虚构日期、金额、对方行为和法条。
- 其他城市/资料不足时不输出本试点城市渠道。

## 2. 二期：多场景与阶段留证

### 2.1 扩展类型

scenario 增加 `early_termination`、`repair_dispute`、`extra_fee`、`agency_service`。先要求用户选择一个主要问题，其余作为相关事实，不在二期直接实现自动多争议诉讼方案。

增加可选 discriminated `scenarioDetails`：

| 类型 | 核心字段 |
| --- | --- |
| early_termination | 退租原因、通知时间、合同期限、双方已提出的责任 |
| repair_dispute | 故障事项、报修时间、原因是否清楚、影响及回应 |
| extra_fee | 费用名称、金额、收费主体、是否约定及是否已支付 |
| agency_service | 服务承诺、收费约定、履约争议、签约和收款主体 |

字段定义随该场景资料核验完成，不提前创造无法使用的问答。多场景不同费用分别记录，金额总计由明确明细计算。

### 2.2 留证模块

按签约、入住、居住、退租四个阶段组织证据目录；每项关联 applicableScenarios 和准备提示。保留设备会话内的完成状态，刷新清除。用户如果需要长期证据保管，应单独立项，不能把浏览器 localStorage 冒充安全证据库。

### 2.3 与合同模块联动

M2 允许把确认过的金额、主体和争议相关条款带入M3。只传最小必要字段，不把整份合同重复发送。前端显示“来自合同提取，待确认”，用户确认后作为 user_statement 提交；原文与用户事实冲突时保留差异。

### 2.4 验收

每个新场景同时具备完整问答、证据项、规则和模板。维修原因未知不等于租客负责；中介收费与个人房东扣押金不混用渠道。改变主体或争议类型后，旧证据和结论重新计算。

## 3. 三期：后续反馈与材料导出

### 3.1 反馈驱动更新

用户选择“对方拒绝/对方未回复/已达成一致/渠道待处理”等状态，形成更新后的 priorActions，重新提交 diagnose-dispute。会话内保持，默认不建设服务器案件库。不声称系统已经跟踪到真实处理进展。

如以后需要跨设备恢复，另行加入经过验证的账号、所有权、保存期限与删除能力；该需求不随三期自动引入。

### 3.2 导出内容

M4 在浏览器生成事实经过、证据目录、协商文本、行动清单、资料版本和来源日期。未填写字段明确保留，缺失证据不显示为已具备。导出件标注用户陈述与辅助建议，不生成承诺成功的律师函或法院制式文书。

### 3.3 RAG 的作用边界

混合检索补充可引用的相关条文，不改变渠道规则的审核条件。检索到其他城市相关案例或政策不能用于本城市渠道资格。规则冲突或资料新旧不明时列为待核实，不由模型投票选择。

### 3.4 验收

用户更新行动状态后产生相应变化；修改前报告不自动变成新事实。导出内容与当前已确认结果一致，包含资料版本且无隐藏个人信息。检索不可用时渠道规则仍可独立执行，输出明确的能力限制。

## 4. 开发任务顺序

固定证据ID与表单字段 → 实现纯规则资格函数 → 构建排序与后续分支 → 确定性协商模板 → 接入M1来源 → 接入M4 → 二期扩展 → 三期反馈与导出。先用合成资料测试分支，再用真实核验资料建立可公开演示的案例。
