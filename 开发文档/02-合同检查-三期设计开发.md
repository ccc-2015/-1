# M2 合同检查：三期设计开发

依赖：00 总体架构、01 资料底座。职责：发现与所选场景有关的合同约定、缺失和不清晰之处，给出可协商的修改方向。原文提取不等于法律效力判断。

## 1. 一期：押金条款检查

### 1.1 用户故事与边界

用户粘贴合同文本，填写试点城市和拟签约/签约日期，查看押金金额、退还安排、扣款条件、不退押金约定四类检查结果。用户可选择“全文”或“片段”，不将用户提供的局部材料视作完整合同。

不上传文件，不比对聊天截图，不做房产真伪核查，不判断最终胜诉可能。合同明确写了押金金额不代表金额合法合理；未匹配到关键词不代表不存在相关约定。

### 1.2 请求

`POST /functions/v1/app?action=analyze-contract`，Content-Type 为 application/json，使用总架构的统一响应外层。

```ts
type AnalyzeContractInput = {
  cityCode: string;
  eventDate: string | null;
  text: string;
  textScope: 'full_contract' | 'excerpt';
  analysisScopes?: Array<'deposit' | 'early_termination' | 'repair' | 'extra_fee' | 'agency_service'>;
};
```

一期 analysisScopes 缺省为 deposit，其他值拒绝并提示当前支持范围。text 必须非空且不超过30000个 UTF-16 code unit；JSON 实际读取字节上限256 KiB，不依赖 Content-Length 强制存在。城市非支持值不是校验错误，而是 coverage=unsupported 并限制结论。

限额为产品初始值，可通过 config 返回给前端；不是对 Sites 平台容量的承诺。

### 1.3 输出

```ts
type ContractFinding = {
  id: string;
  category: 'deposit_amount' | 'deposit_return' | 'deposit_deduction' | 'deposit_forfeit';
  checkStatus: 'clear' | 'ambiguous' | 'not_found' | 'needs_verification';
  priority: 'high' | 'medium' | 'notice' | 'unrated';
  legalAssessment: 'potential_legal_issue' | 'unfavorable_term' |
    'unclear_or_missing' | 'not_assessed';
  excerpts: Array<{ text: string; start: number; end: number }>;
  explanation: string;
  suggestedQuestions: string[];
  negotiationSuggestion: string | null;
  sourceRefs: Array<{ sourceId: string; articleIds: string[] }>;
  missingFacts: string[];
};

type ContractAnalysis = {
  findings: ContractFinding[];
  summary: { needsAttention: number; needsConfirmation: number };
  extractedFacts: {
    depositAmountCents: number | null;
    returnTimingText: string | null;
    deductionItems: string[];
  };
  evidenceChecklist: Array<{ evidenceId: string; title: string; reason: string }>;
  references: SourceRecordPublic[];
};
```

SourceRecordPublic 的精确定义见00总体架构，M1负责按该结构输出审核后的公开字段。summary 只是计数，不是风险百分比。clear 表示这一项约定在给定文本中较清楚，不代表合同安全或合法。high 表示优先核实/协商，不代表当然违法。sourceRefs 可以为空，此时只描述合同表述或一般协商建议。

### 1.4 处理流程

1. 校验请求及日期，保留收到的原始 text。
2. 在处理副本中做空白归一化、段落切分，并保留到原文的偏移映射。
3. 通过“押金、保证金、退还、扣除”等词和上下文规则获取候选段落；保留否定语义和相邻条件。
4. AI 输出受限结构：候选约定、原文引句、金额及条件；不允许生成网址、电话或新法条。
5. 服务端在原始 text 查找引句并计算 start/end；重复匹配时标记歧义或纳入所有相关位置，不使用未经校验的模型偏移。
6. M1 按地域、场景、事件日期选择可用资料；规则结合明确事实生成检查项。
7. 将允许的资料和检查结果交给模型生成解释；模型不能新增没有原文/规则支撑的检查项。
8. 校验输出结构、引用ID、原文定位、金额来源及必需字段，回填来源快照，生成计数。

一期建议拆成“提取”和“受约束解释”两个逻辑步骤。可以合并为一次模型请求以降低成本，但服务端仍独立执行原文与引用校验；是否合并以真实请求质量和耗时决定。

### 1.5 原文定位约定

start/end 使用 JavaScript 字符串 UTF-16 索引，左闭右开，必须满足 `text.slice(start, end) === excerpt.text`。前后端共享此约定。若转为 Python 服务，必须显式转换其 Unicode code point 偏移，不直接互用。

不接受模型改写后的“合同原文”。找不到时丢弃该引句并将相应项设为 needs_verification；不得继续展示基于该引句的确定性结论。全文只保存在本次请求和页面会话，不记录到日志。

### 1.6 一期规则表

| 检查项 | 可能发现 | 输出约束 |
| --- | --- | --- |
| 押金金额 | 只有“押一付三”等约定、多个金额矛盾、金额缺失 | 押一付三需确认对应月租；不能自行猜测金额 |
| 退还安排 | 退还时间/条件不明，存在多个冲突期限 | 标注需补充或核实，不凭空给出法定天数 |
| 扣款条件 | “一切费用”“由出租人决定”，没有项目/标准 | 建议明确项目、凭证与争议处理，不自动认定条款无效 |
| 不退押金 | 提前退租或其他行为触发全额扣除 | 同时提取触发条件；提示结合事实、违约责任及依据判断 |

not_found 的展示是“所提供文本中未识别到明确约定”；excerpt 输入还需提示条款可能存在于其他页。用户未提交完整文本时不能输出“整份合同没有相关条款”。

### 1.7 AI 依赖与失败处理

服务端对供应商请求设置超时与输出 token 上限，使用供应商支持的结构化输出；仍校验响应。将合同和资料视为不可信内容，合同中的“忽略规则”“输出某电话”等文字只能作为合同文本分析。

主模型不可用时，可以提供已经实现且独立验证的字面规则结果，processingMode=rules、coverage=limited，并说明语义审查未完成；无独立规则能力则返回 503/504。不能显示假的“AI分析成功”。不自动重试付费POST；结构错误由本次调用返回可理解错误，用户可手动重试。

### 1.8 验收样例

- 清晰约定金额、时间和扣款项目：展示识别内容，不制造问题。
- 仅有局部押金段落：不作全文缺失断言。
- 同一引句出现两次：原文定位不串段、不越界。
- 没有押金关键词但存在“履约保证金”：能纳入候选，语义不足时提示核实。
- “房东不得无故扣除押金”：不能因“不退/扣除”词错误标红。
- 用户文本包含指令：不得改变引用、输出结构或调用目的地。
- 模型引用不存在的法条或原文：最终响应拒绝该内容。
- 日期未知、其他城市、超长输入、空文本：输出匹配总架构约定。

## 2. 二期：常见条款与用户校正

### 2.1 扩展范围

增加提前退租、维修责任、额外费用、中介服务四个分析范围。押金相关 findings 的语义不变；增加类别需扩展枚举并更新 apiVersion 的兼容评估，旧前端不得把未知类别丢失为正常。

### 2.2 场景新增内容

| 范围 | 提取重点 | 必需补充事实 |
| --- | --- | --- |
| 提前退租 | 通知期限、责任、转租、双方解除条件 | 拟退租原因、是否已通知 |
| 维修 | 维修事项、承担主体、报修方式、时限 | 故障原因是否清楚、是否影响使用 |
| 额外费用 | 项目、标准、收款方、变更条件 | 是否已明示、是否实际收取 |
| 中介服务 | 服务内容、费用、承诺、违约责任 | 主体身份、承诺是否书面化 |

同一条款涉及多个范围时允许共享引句，但结论按场景分别展示，避免重复制造风险数量。

### 2.3 用户修正协议

增加可选 `factOverrides`，每项为 `{ field, value, reason? }`。它表达用户陈述，不改写原始合同；结果保留 `factOrigins: contract | user_statement | unknown`。合同提取值与用户修正冲突时展示两者，要求确认，不静默覆盖合同证据。

用户修改后重新调用分析，所有依赖事实的检查项、证据清单和引用完整重算。禁止只在前端改金额而保留旧建议。

### 2.4 验收

每个新增范围都有正常、模糊、缺失和相互冲突样例。自然损耗不能仅依据合同关键词判为人为损坏；提前退租责任不能仅依据是否扣押金得出。规则无法处理的事实进入 missingFacts。

## 3. 三期：PDF/OCR 输入和法规检索

### 3.1 输入扩展流程

选择文件 → 本地格式/大小/页数检查 → 提取文字 → 用户校对 → 组装同一 AnalyzeContractInput → 常规分析。OCR输出只生成草稿文本，不直接触发法律分析，用户需明确确认。

默认先在浏览器用 PDF.js 读取有文本层的PDF。扫描件与图片经后端调用OCR API。云端处理前说明数据将发送给第三方；关闭第三方处理时允许改用粘贴文本。

### 3.2 文件接口

`POST /functions/v1/app?action=extract-document`，multipart/form-data，一次一个文件。产品初始上限：5 MiB、10页，允许 PDF/JPEG/PNG，拒绝加密PDF、破损文件和无法验证的格式。客户端检查只改善体验，服务端再次限制真实字节并校验文件特征；解压/渲染的页数、像素和执行时间也须限制。

```ts
type ExtractionResult = {
  draftText: string;
  pages: Array<{
    page: number;
    text: string;
    warnings: string[];
    quality: 'acceptable' | 'needs_review' | 'unknown';
  }>;
  provider: 'browser_pdf' | 'cloud_ocr';
  warnings: string[];
};
```

不同供应商置信度不可直接比较，没提供可靠指标时 quality=unknown。浏览器本地提取也统一为此结构。分析结果定位针对用户确认后的文本，不声称对应原扫描文件的法庭证据定位。

### 3.3 运行限制与可选异步

一期无文件端点；三期先验证函数实际请求体、执行时间、内存以及供应商响应时间。文件上限为产品约束，不表示平台必然支持。受限同步流程不能稳定完成时，先缩小同步支持范围并提示，不在函数返回后偷偷继续处理。

只有必须异步时才新增任务服务：提交任务返回202和jobId，任务查询需验证所有权与有效期，worker处理超时/取消/清理，客户端按服务给出的间隔查询。匿名jobId不是访问权限。此分支需要独立设计与资源验证后才能上线。

### 3.4 RAG 接入

只替换资料候选召回，不改变原文定位、规则、引用校验和用户确认步骤。接入 M1 的混合检索，检索不到适用条文时返回事实描述与待核实项，不通过相似但不适用条文强行生成法律结论。

### 3.5 验收

文字PDF、扫描PDF、模糊图片、金额识别错误、旋转页、超过页数、识别后文本超30000字符、供应商超时均有明确结果；超限文本不静默截断，提示用户选择相关页或片段。用户校正金额后，报告金额同步变化；未确认草稿不得触发分析。

## 4. 开发任务顺序

1. 定义请求/响应契约和样例。
2. 实现字面检查、原文定位及金额校验。
3. 接入M1候选资料及引用闭合检查。
4. 接入一次真实模型调用，验证结构化输出及脱敏错误处理。
5. 连接M4表单与结果展示。
6. 二期按场景增加字段、规则及用户修正。
7. 三期在原接口之前增加提取/校对，不重写分析链路。
